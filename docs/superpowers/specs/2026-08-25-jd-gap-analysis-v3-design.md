# JD 差距分析 V3 设计规格

**日期：** 2026-08-25  
**状态：** 已由用户确认，进入实施计划
**版本标识：** `jd-analysis-v3`、`resume-gap-v3`  
**产品范围：** 求职搭子 / CareerMint 的 JD 结构化、简历证据比对与差距展示

## 1. 背景与问题

生产环境中的一个真实案例包含 5 条 JD 要求。现有分析将 5 条全部判为“部分匹配”，其中 0 条为“有证据”、0 条为“没有证据”、0 条为“需要判断”。页面并未隐藏不匹配项；根因是模型把宽泛相关性当成了部分匹配。

当前实现还存在三个结构性问题：

1. 一个 Prompt 同时负责提取 JD、翻译、匹配职业档案，任务过多，错误难定位。
2. 匹配主要依赖已确认职业档案，而用户为本次申请选择的简历没有成为首要证据，因此无法准确回答“这份简历与这个岗位差在哪里”。
3. `partial` 的约束过宽。只要职业经历大致相关，模型就可能输出部分匹配；程序只验证事实 ID 是否存在，没有验证证据能否支持具体要求。

JD 差距分析是产品核心。本版本的目标不是增加更多文字，而是建立可解释、可验证、能区分不同要求严格程度的分析方法。

## 2. 目标

- 以用户为本次申请选定的简历作为首要对照依据。
- 将已确认职业档案作为补充来源，并明确区分“档案中有、简历中没写”。
- 把复合要求拆为原子子条件，再逐项判断覆盖情况。
- 同时展示覆盖程度与缺口影响，不使用虚假的百分比分数。
- 对学位、年限、语言、许可、工具、行业、职责等类别采用不同严格度。
- 每个“完全匹配”或“部分匹配”都必须有可在原文中验证的简历引用。
- 说明具体覆盖了什么、缺少什么、为什么不完全匹配，以及需要用户确认什么。
- 通过少量、高价值的匿名评测比较精选 Prompt，选择满足硬性质量门槛且误报最少的版本。
- 保持用户主动触发、结果缓存、成本可追踪和事实安全规则。

## 3. 非目标

- 不生成简历改写建议，不自动修改简历。
- 不自动把简历内容写入职业档案。
- 不用模型替用户确认工作许可、语言水平、证书状态或其他个人事实。
- 不生成综合匹配百分比或录取概率。
- 不新增第三次 AI 调用；新架构复用现有的 JD 分析与简历差距两个调用阶段。
- 不自动抓取招聘网站，不自动投递。
- 不在本规格中重做全站视觉设计。

## 4. 核心术语

- **JD 快照：** 申请创建时保存的不可变岗位原文。
- **对照简历：** 用户为当前申请选择或上传的简历版本，是覆盖判断的首要证据。
- **职业档案事实：** 用户已确认、带来源的个人事实，只用于补充说明。
- **要求：** 从 JD 中提取的一项职责、资格、技能或条件。
- **原子子条件：** 一条要求内可独立判断的最小条件。例如“3 年 SQL 和 Tableau 经验”拆成工作年限、SQL、Tableau 三项。
- **覆盖状态：** `complete`、`partial`、`none`、`needs_confirmation`。
- **影响等级：** `blocking`、`important`、`minor`。
- **简历证据：** 可在对照简历文本中精确回查的引用。
- **档案补充：** 已确认职业档案中能支持要求，但当前简历未充分表达的事实。

## 5. 总体架构

系统采用两个 AI 阶段，加一个确定性校验层。

### 5.1 阶段一：JD 结构化

阶段一只读取 JD 快照，不读取简历或职业档案。它负责：

- 生成完整中文翻译；
- 提取所有要求，保留原文和中文翻译；
- 标记要求类别与 `required`、`core`、`preferred` 类型；
- 将复合要求拆成原子子条件；
- 标记 JD 是否明确允许相关、相近、可比或替代条件；
- 识别是否属于明确的硬门槛；
- 为阶段二提供稳定的要求 ID、顺序和原文引用。

阶段一不得判断用户是否匹配，也不得看到用户材料。

### 5.2 阶段二：证据比对

阶段二读取：

- 阶段一产生的结构化要求与原子子条件；
- 当前申请的对照简历文本；
- 用户已确认的职业档案事实。

它逐个原子子条件输出：

- 简历中是否有直接证据；
- 简历精确引用；
- 职业档案是否有补充证据；
- 相关职业事实 ID；
- 缺口类型；
- 简短判断理由；
- 必要时需要向用户确认的问题。

阶段二不得新增要求、合并要求或遗漏要求。职业档案只能作为单独的补充说明，不能提高“当前简历覆盖状态”。

### 5.3 确定性校验与聚合

程序对模型结果执行：

1. 要求 ID 与子条件 ID 完整性校验；
2. 去重和未知 ID 拒绝；
3. 简历引用的安全归一化与原文回查；
4. 职业事实 ID 所有权、确认状态和存在性校验；
5. 按固定规则聚合子条件，计算要求级覆盖状态；
6. 按 JD 类型和类别规则计算影响等级；
7. 对无效证据降级，而不是保留模型给出的乐观状态。

最终展示状态由程序产生，模型不得直接决定最终要求级结论。

### 5.4 用户操作顺序

一次新申请的分析顺序固定为：

1. 用户添加并保存 JD；
2. 用户上传新简历或选择已有简历；
3. 用户在分析前预览所选简历的解析内容，确认选对版本；
4. 用户点击 **开始 JD 差距分析**；
5. 系统依次执行仍需运行的阶段一和阶段二，并展示结果。

选择简历发生在分析之前。没有对照简历时按钮不发起证据比对，并提示先选择简历。简历预览读取私有文件的安全预览或已解析文本，不公开原始文件地址。更换简历会使旧差距结果过期，但不会删除旧文件、旧分析或其他申请的对照简历。

## 6. 数据契约

### 6.1 阶段一输出

每项要求至少包含：

- `requirementId`
- `category`
- `requirementType`: `required | core | preferred`
- `originalText`
- `translationZh`
- `sourceExcerpt`
- `allowsEquivalent`: JD 是否明确允许相近或可比条件
- `explicitGate`: 是否为明确硬门槛
- `criteria[]`

每个原子子条件至少包含：

- `criterionId`
- `kind`: 学位层级、专业、年限、语言、许可、证书、工具、职责、行业、软技能、量化成果或其他
- `originalText`
- `translationZh`
- 可验证的结构化约束，例如年限、语言级别、指定工具或证书名称

阶段一输出必须保证：

- 每条 JD 要求只出现一次；
- 每条要求至少有一个子条件；
- 原文引用可在 JD 快照中回查；
- 中文翻译不增加或删除限定条件；
- 薪资、地点等信息若只是岗位信息而非候选人条件，不混入差距评分。

### 6.2 阶段二输出

每个原子子条件恰好返回一项：

- `criterionId`
- `resumeEvidenceStatus`: `direct | partial_direct | none | needs_confirmation`
- `resumeExcerpt`: 精确引用或 `null`
- `profileFactIds[]`
- `gapType`: `missing_from_resume | too_vague | missing_result_or_number | no_supporting_fact | language_or_authorization_confirmation | none`
- `reasonZh`
- `userQuestionZh`: 必要时存在，否则为 `null`

模型不得仅凭关键词、职位名称或泛化相关性返回 `direct` 或 `partial_direct`。

### 6.3 要求级展示结果

每项要求最终展示：

- 原文与中文翻译；
- 要求类型；
- 原子子条件；
- 覆盖状态；
- 影响等级；
- 简历精确引用；
- 单独标记的职业档案补充；
- 已覆盖子条件；
- 缺失子条件；
- 缺口类型；
- 简洁理由；
- 需要用户回答的问题。

## 7. 确定性覆盖规则

### 7.1 完全匹配

只有全部必需子条件均存在有效简历直接证据时，要求级状态才是 `complete`。职业档案证据不能代替简历证据。

### 7.2 部分匹配

只有至少一个必需子条件存在有效简历直接证据，同时至少一个必需子条件缺失、证据过弱或需要确认时，状态才是 `partial`。

仅有主题相关、相似职位名称、同领域背景或职业档案事实，不足以形成 `partial`。

### 7.3 没有证据

全部必需子条件均无有效简历直接证据时，状态为 `none`。如果职业档案有支持，界面显示“职业档案有补充，但当前简历未体现”，状态仍为 `none`。

### 7.4 需要确认

要求主要依赖用户本人判断，且简历与职业档案均无法确定时，状态为 `needs_confirmation`。典型情况是工作许可、搬迁意愿或未标明级别的语言能力。

### 7.5 引用校验

- `complete` 和 `partial` 必须至少包含一个有效简历引用。
- 引用经过 Unicode 归一化、空白归一化和安全标点归一化后，必须能在简历解析文本中找到。
- 只允许有限的换行与连续空格差异；不允许模型改写后冒充引用。
- 无法验证的引用被删除，相应子条件降为 `none` 或 `needs_confirmation`。

## 8. 分类严格度矩阵

| 类别 | 判断规则 |
|---|---|
| 学位层级 | 严格区分本科、硕士、在读与已毕业；不能相互替代。 |
| 学位专业 | 仅当 JD 明确出现“相关、相近、可比、equivalent、comparable、oder vergleichbar”等许可表述时，允许语义等价专业完全匹配；若 JD 指定唯一专业则严格判断，边界情况转为需要确认。商业信息学与 JD 允许的商业、数据、信息系统等可比专业可按语义证据判断。 |
| 工作年限 | 数字严格；项目数量、课程时间不能替代工作年限。证据不足时不得推算。 |
| 语言 | 严格判断明确级别；“流利”“专业工作能力”等描述可映射到范围，但必须解释映射，无法确认具体门槛时转为需要确认。 |
| 工作许可 | 只能使用用户明确确认的事实，否则一律需要确认。 |
| 证书与执照 | 名称、有效状态及必要级别严格匹配。 |
| 指定工具 | 默认严格；只有 JD 明确接受替代工具时才允许等价判断。 |
| 职责与业务能力 | 允许同义表达，但必须能证明相同动作，并至少体现相同业务场景或结果之一。纯关键词不算证据。 |
| 行业经验 | 同行业可完全覆盖；相邻行业最高为部分覆盖；无行业场景不得凭岗位名推断。 |
| 软技能 | 必须有行为、项目或结果证据，不能只凭“沟通能力强”等自评关键词。 |
| 量化成果 | JD 明确要求规模、增长、节省、指标或业绩时，简历没有数字或可核验结果，最高为部分覆盖。 |
| 加分项 | 使用同一证据规则，但缺失影响只能是 `minor`，不能成为阻断项。 |

## 9. 影响等级规则

- `blocking`：仅用于 JD 明确写明的必需门槛，例如法定许可、必需证照、明确最低语言级别、明确最低年限或不可替代的学位条件；缺失或未确认时才成立。
- `important`：核心职责、主要技能或强要求存在实质缺口，但 JD 没有表明会直接淘汰。
- `minor`：加分项、偏好项、低影响措辞或证据表达不足。

覆盖状态和影响等级是两条独立轴。例如一项要求可以是“没有证据 + minor”，也可以是“部分匹配 + blocking”。系统不把影响等级伪装成匹配概率。

## 10. 页面设计

### 10.1 标题与导航

- 应用级标签继续使用 `JD`，减少导航变化。
- 页面主标题改为 **JD 差距分析**。
- 页面显示当前对照简历文件名；未选择时明确显示“尚未选择对照简历”。
- 局部标签为 **待补差距**、**全部要求**、**JD 内容**。

### 10.2 摘要

摘要展示：

- 总要求数；
- 完全匹配；
- 部分匹配；
- 没有覆盖；
- 阻断差距。

不再只显示“有证据 / 需要关注”，避免掩盖覆盖程度。

### 10.3 默认视图

`待补差距` 默认按以下顺序分组：

1. 阻断；
2. 重要；
3. 次要；
4. 已完全覆盖，默认折叠。

组内优先显示 `none`，再显示 `needs_confirmation`，最后显示 `partial`。不能静默只展示五条；如果为首屏简洁进行折叠，必须显示“还有 N 条”并允许一次展开。

### 10.4 要求卡片

收起状态显示：

- 中文翻译为主；
- 原文为次；
- 覆盖状态文字；
- 影响等级文字；
- 已覆盖与缺失子条件的简短计数。

展开后依次显示：

1. 原子子条件及逐项状态；
2. 简历原文引用；
3. 单独的职业档案补充；
4. 缺口说明；
5. 需要用户确认的问题。

状态不能只依赖颜色。展开控件支持键盘与 `aria-expanded`。移动端保持单栏阅读。

### 10.5 旧版结果

旧版结果仍可读取，但页面清楚标记：**这是旧版分析，请重新分析以查看详细差距。**

旧结果不能通过前端推断伪装成 V3 结果，也不能自动触发新分析。

## 11. 数据流、缓存与版本

### 11.1 保存内容

V3 保存：

- JD 快照 ID 与哈希；
- 阶段一 Prompt 与结构版本；
- 对照简历资源 ID、文件哈希与文件名快照；
- 已确认职业事实指纹；
- 原子子条件；
- 子条件级证据判断；
- 最终确定性聚合结果；
- 模型、Token、估算成本、状态和稳定错误码。

具体迁移可扩展现有规范化 requirement 与 gap 数据表，增加 criteria 和 assessment 记录。表名、索引和 RPC 细节在实现计划中确定，但必须继续使用 owner-scoped RLS 和同用户所有权校验。

### 11.2 缓存键

只有以下内容全部相同时复用成功结果：

- JD 快照哈希；
- 对照简历文件哈希；
- 已确认职业事实指纹；
- 阶段一和阶段二版本；
- Provider 与模型。

JD 变化、对照简历变化、职业事实确认状态变化或 Prompt 版本变化时，结果标记为过期，并提示用户重新分析。系统不自动调用 AI。

### 11.3 调用次数

一次全新分析最多包含两个模型调用：

1. JD 结构化；
2. 证据比对。

如果阶段一的 JD 结构化结果仍有效，只运行阶段二。重复点击、相同输入的进行中任务和相同成功结果必须复用，不重复扣费。

## 12. 错误处理

- 阶段一输出缺失要求、重复要求、无效 JD 引用或结构错误时，自动重试一次。
- 阶段二缺少子条件、出现未知 ID、重复判断或结构错误时，自动重试一次。
- 二次失败后保留上一次成功结果，标记其输入版本，并展示可重试提示。
- 单条简历引用无效时，程序删除该引用并降级对应判断；不能让一条无效引用污染其他要求。
- 没有对照简历时，不运行覆盖分析，提示用户选择简历。
- 简历解析失败时保留文件与 JD；允许重新解析、浏览器本地 OCR、粘贴文字或换文件。
- AI 错误不得在界面或普通日志暴露 Provider 响应、完整 JD、完整简历或职业事实正文。

## 13. Prompt 设计与精简评测

### 13.1 精选 Prompt

阶段一使用一份固定的严格结构化 Prompt，并通过要求召回、原子拆分和 JD 引用硬门槛验证。主要误判发生在证据比对，因此精简评测只横向比较三个经过设计的阶段二候选 Prompt：

- **P1：分类规则版** — 明确两阶段输出、原子子条件、严格度矩阵和禁止推断规则，作为简洁基线。
- **P2：规则 + 对比例版** — 在 P1 基础上加入少量高价值正反例，重点示范专业语义等价、宽泛相关不算部分匹配、档案证据不提高简历覆盖。
- **P3：规则 + 对比例 + 同次自检版** — 在 P2 基础上要求模型在输出前检查子条件完整性、引用存在性和过度匹配，但仍只返回一次 JSON，不新增模型调用。

不进行无边界 Prompt 搜索，不让模型自动生成大量候选，也不把所有措辞差异都当成新版本。

### 13.2 精简样例集

基础评测使用 6 个不可逆匿名化的组合样例，每个样例覆盖多个边界条件：

1. 英文复合职责、指定工具与量化成果；
2. 德文专业要求，同时包含明确允许 `vergleichbar` 与指定唯一专业的对照；
3. 工作年限、指定证书与不可替代工具；
4. 语言级别、描述性语言能力与工作许可；
5. 同行业职责同义表达、行业经验与有行为证据的软技能；
6. 相邻行业、关键词相似但实质不匹配的误报陷阱，并包含只有职业档案证据的条件。

每个样例包含人工确认的：要求拆分、合法引用、期望覆盖状态、影响等级和关键差距。真实材料只能用于本地匿名化，不把原始 JD、简历或职业事实写入代码仓库、普通日志或评测报告。

### 13.3 调用预算

- 固定阶段一 Prompt 对 6 个样例各运行一次，共 6 次结构化调用；结构化结果被三个阶段二候选复用。
- 6 个结构化结果 × 3 个阶段二 Prompt，共 18 次证据比对调用。
- 基础评测合计 24 次调用。
- 只在阶段一硬门槛失败、候选结果接近或存在稳定性疑问时追加复测，最多 6 次。
- 总上限为 30 次模型调用。
- API 费用硬上限为 **2 美元**；达到上限前程序停止发起新请求，并保存已完成结果。
- 每次记录输入、输出 Token、缓存命中、延迟和估算费用，但不记录原始敏感文本。

按 2026-08-25 采集的官方价格，实际精简评测预计显著低于 2 美元。价格必须读取配置，不能写死在业务代码中。价格来源：[DeepSeek API Pricing](https://api-docs.deepseek.com/quick_start/pricing/)。

### 13.4 评分与硬门槛

评分优先级：

1. 误把不匹配判成匹配的假阳性，权重最高；
2. JD 要求提取召回率；
3. 原子拆分正确性；
4. 简历引用有效率；
5. 差距说明准确性；
6. 边界样例稳定性；
7. Token、成本和延迟。

所有候选都必须满足：

- 无效简历引用为 0；
- 全部子条件有有效简历证据时才允许完全匹配；
- 职业档案证据不能提高简历覆盖；
- 所有输入要求和子条件恰好输出一次；
- 加分项缺失不能被判为阻断。

不满足硬门槛的 Prompt 直接淘汰，不因综合分高而上线。满足门槛的候选中，选择假阳性最少者；若相同，再比较要求召回、差距说明、稳定性，最后才比较成本与延迟。

## 14. 隐私与安全

- 只向 AI 发送完成当前阶段所需的文本。
- 不把完整简历、JD、职业档案或 Provider 原始响应写入普通日志。
- 评测仓库只保存不可逆匿名化样例与人工标签。
- 所有用户数据查询与写入继续受 RLS、用户所有权和服务端校验保护。
- 模型输出始终视为不可信输入，经过结构、来源、ID 与引用校验后才能保存和展示。
- AI 不得虚构经历、数字、技能、证书、许可或面试故事。

## 15. 测试策略

### 15.1 单元测试

- 复合要求原子拆分与完整性校验；
- 各类别严格度矩阵；
- `complete`、`partial`、`none`、`needs_confirmation` 聚合规则；
- `blocking`、`important`、`minor` 影响规则；
- 引用归一化与精确回查；
- 职业档案只能补充、不能升级覆盖；
- 无效证据降级；
- 缓存键和过期判断；
- 排序、计数和展开数量提示。

### 15.2 数据与服务测试

- 所有要求和子条件一一对应；
- 未知、重复或缺失 ID 安全失败；
- 用户只能访问自己的简历、事实、分析和申请；
- 同输入复用结果，进行中任务不重复创建；
- 上一次成功结果在新调用失败后保留；
- 旧版本结果可读且被标记为旧版；
- Token 与成本记录不含敏感原文；
- CI 使用 mock Provider，不产生真实 API 费用。

### 15.3 端到端测试

- 英文与德文 JD；
- 复合要求；
- 明确允许相近专业与指定唯一专业；
- 年限、语言、工作许可、证书和工具；
- 简历有证据、只有档案证据、完全无证据；
- 对照简历或职业事实变化后的过期提示与手动重跑；
- 桌面和移动端的分组、折叠、键盘操作与中文/原文显示。

## 16. 迁移与发布

1. 新增 V3 数据结构和版本字段，不覆盖旧分析。
2. 先在 mock 与匿名本地样例上通过确定性测试。
3. 使用 6 次固定阶段一结构化调用和 18 次阶段二 Prompt 对比调用；只有必要时追加最多 6 次修正或边界复测。
4. 选出满足全部硬门槛的 Prompt，并固定版本与评测摘要。
5. 在 Preview 环境验证真实流程、成本记录和旧数据兼容。
6. 部署生产后仅由用户点击触发 V3 分析。
7. 若 V3 失败，保留旧成功结果和用户材料，允许回退到上一稳定 Provider 方法；不回写伪造的新状态。

## 17. 验收标准

当以下条件全部满足时，本功能可以完成：

- 页面标题为“JD 差距分析”，默认直接展示待补差距。
- 每条要求都同时显示覆盖状态与影响等级。
- 复合要求被拆为可解释的原子子条件。
- “部分匹配”必须有至少一条有效简历直接证据和至少一项明确缺口。
- “完全匹配”必须覆盖全部必需子条件。
- 商业信息学等专业只有在 JD 明确允许相关或可比专业时才能按语义等价判断。
- 档案中的事实被单独显示，不能把当前简历从未覆盖升级为部分或完全覆盖。
- 年限、语言、许可、证书和指定工具按严格规则处理。
- 所有简历引用均可在解析文本中回查。
- 不匹配项不会被过滤或静默截断，已匹配项在底部折叠。
- 旧版分析清楚标记并可由用户主动重新分析。
- 精简评测不超过 30 次真实调用，费用不超过 2 美元，并能说明最终 Prompt 的选择依据。
- 相同输入复用结果；系统不自动调用 AI。
- 正常日志、错误响应和评测提交中没有完整 JD、简历或职业档案内容。
