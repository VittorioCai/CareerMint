# 海外求职助手 MVP 设计

- 日期：2026-08-13
- 状态：产品设计已由用户逐段确认
- 首发用户：申请英语国家岗位的中文求职者
- 首发形态：桌面优先、兼容手机的 Web App

## 1. 产品定义

产品以“职业档案”为可信事实来源，根据招聘 JD 生成可追溯的英文定制简历，把最终简历与具体投递记录关联，并在进入面试准备阶段后复用共享题库、生成岗位特定题目和基于真实经历的回答提纲。

产品不是自由改写器。它的核心价值是让用户持续积累可复用的职业事实，并建立以下完整数据链路：

```text
职业事实
  -> JD 匹配
  -> 定制简历版本
  -> 投递记录
  -> 面试准备
  -> 申请结果与统计
```

## 2. 已选产品路线

讨论过三条路线：

1. 仅做 JD 简历改写：上线最快，但差异化和留存较弱。
2. 先做投递追踪：实现简单，但缺少首次使用时的强价值感知。
3. 以职业档案为中心，分阶段加入简历定制、投递追踪和面试准备。

采用路线 3。它的初始范围更大，因此必须按可独立验证的纵向功能切片交付，不同时开发浏览器扩展、外部同步和语音面试。

## 3. 目标与非目标

### 3.1 MVP 目标

- 将用户已有简历解析为结构化职业档案。
- 让用户确认、修正并补充职业事实。
- 从英文 JD 中提取硬性要求、加分项、职责和关键词。
- 将岗位要求与已确认事实匹配，明确展示证据和能力缺口。
- 生成每条都有来源的英文定制简历建议。
- 支持逐条接受、编辑、拒绝，以及 DOCX/PDF 导出。
- 导出后通过一次确认创建对应的投递记录。
- 手动追踪申请阶段、联系人、日期、备注和下一步行动。
- 为每个岗位组合通用题、职能题和岗位特定题。
- 基于职业档案生成回答提纲，不生成需要用户背诵的虚假故事。
- 汇总投递量、回复率、面试率、Offer 率、渠道表现和阶段耗时。

### 3.2 MVP 非目标

- 浏览器扩展和招聘网站自动抓取。
- 邮箱、LinkedIn、Google Drive 和日历同步。
- 自动投递。
- 完整求职信生成。
- 德文或其他非英文简历。
- 语音模拟面试和语音评分。
- 自动修改未经用户确认的职业档案。
- 根据少量申请数据声称某个简历版本必然导致更高转化。

## 4. 核心用户流程

### 4.1 首次建档

1. 用户上传 PDF 或 DOCX 原始简历。
2. 系统解析基本信息、教育、工作、项目、技能和成果。
3. 所有解析结果先标记为“待确认”。
4. 用户检查、修正并确认事实。
5. 系统提示缺少数据的经历，用户可以现在补充，也可以稍后在匹配 JD 时补充。
6. 用户形成可持续维护的职业档案。

### 4.2 创建申请与定制简历

1. 用户粘贴英文 JD。
2. 系统提取公司、职位、地点、职责、硬性要求、加分项和关键词。
3. 用户确认公司与岗位信息。
4. 系统为每项要求标记“有证据”“部分匹配”或“没有证据”。
5. 对必要但信息不足的经历，系统提出补充问题。
6. 系统仅使用已确认事实生成逐条修改建议。
7. 用户查看原文、建议文本、理由和事实来源，逐条接受、编辑或拒绝。
8. 用户导出最终 DOCX 或 PDF。
9. 系统展示“记录本次申请”，自动带入 JD、岗位、日期和最终简历版本；用户确认后建立投递记录。

### 4.3 追踪与面试准备

1. 用户在看板或详情页手动更新申请状态。
2. 每个申请的详情页保留 JD 快照、简历版本、联系人、备注和时间线。
3. 系统为该岗位调用共享的通用题和职能题。
4. 系统根据 JD 生成岗位特定题，经过语义去重后才写入共享题库。
5. 系统从已确认事实与 STAR 故事中选择证据，形成该岗位的回答提纲。
6. 用户记录准备状态和个人笔记；通用回答的更新可以由用户选择同步到其他岗位。

## 5. 信息架构

主导航只保留：

- 首页
- 我的投递
- 职业档案
- 面试题库

全局主操作是“新建申请”。简历生成不作为孤立页面存在，而是始终属于一个申请草稿。

### 5.1 首页

- 新建申请入口。
- 待办事项和需要跟进的申请。
- 最近使用的岗位。
- 基础投递统计。

### 5.2 职业档案

- 基本信息、教育、工作经历、项目、技能、证书和语言。
- 可量化成果。
- STAR 故事。
- 每条事实的确认状态和来源。
- 档案完整度仅作引导，不阻止用户继续。

### 5.3 我的投递

默认看板阶段：

```text
准备中 -> 已投递 -> HR 沟通 -> 面试 -> Offer
                              \-> 已拒绝 / 已撤回
```

同时提供表格视图，支持按公司、岗位类型、日期、阶段和渠道筛选。

### 5.4 投递详情

- 概览：公司、职位、状态、日期、来源和下一步行动。
- JD：原始快照与结构化要求。
- 简历：生成历史和最终投递版本。
- 面试准备：题目清单、回答提纲、准备状态和笔记。
- 记录：联系人、面试安排、反馈和时间线。

### 5.5 面试题库

- 通用题、职能题、岗位特定题。
- 一个核心题可以包含多个常见问法。
- 题目只存一次；不同岗位通过关联记录复用。
- 每个岗位单独保存优先级、准备状态、回答提纲和备注。

## 6. 系统边界与模块

| 模块 | 单一职责 |
| --- | --- |
| 职业档案 | 保存、确认和维护用户职业事实 |
| JD 分析 | 将不可信的 JD 文本解析为结构化岗位要求 |
| 匹配与简历定制 | 选择相关事实，生成并验证有来源的修改建议 |
| 文档版本与导出 | 保存不可变版本，生成 DOCX/PDF |
| 投递追踪 | 管理岗位、阶段、联系人、日期、备注与时间线 |
| 面试准备 | 管理规范化题库、岗位题单和回答提纲 |
| 统计 | 从申请与状态事件中计算汇总指标 |

各模块通过明确的数据接口协作。AI 不能直接任意写数据库；AI 输出必须先通过结构校验和事实校验，再作为草稿交给用户。

## 7. 核心数据模型

### 7.1 职业数据

- `CareerProfile`：用户的职业档案根对象。
- `CareerFact`：最小可引用事实，包含类型、内容、时间、来源和确认状态。
- `Experience`：工作或实习经历。
- `Project`：项目经历。
- `Achievement`：与经历或项目关联的量化成果。
- `Skill`：技能、熟练度和证据关联。
- `Story`：结构化 STAR 故事及其事实引用。
- `SourceAsset`：上传的原始简历文件及解析状态。

`CareerFact.confirmation_status` 只能是：

- `pending`：解析得到但未经用户确认。
- `confirmed`：用户确认真实，可用于确定性陈述。
- `needs_detail`：事实方向存在，但缺少足够信息。

### 7.2 岗位与简历

- `JobApplication`：公司、职位、地点、来源、阶段、关键日期和下一步行动。
- `JobDescriptionSnapshot`：创建申请时保存的 JD 原文及结构化要求。
- `RequirementMatch`：岗位要求、匹配状态和证据事实引用。
- `ResumeVersion`：每次生成或编辑后的不可变快照及版本号。
- `ResumeContentItem`：简历中的摘要、经历要点或技能项。
- `ResumeContentEvidence`：内容项到一个或多个已确认事实的关联。

生成后的用户编辑不会自动更新职业档案。纯措辞调整可以直接形成新版本；如果编辑新增或改变数字、日期、公司、职位、技能或其他事实，导出前必须关联已有事实，或由用户明确确认并新增 `CareerFact`。只有用户选择“保存到职业档案”并完成确认后，新事实才可被未来申请复用。

### 7.3 题库与回答

- `InterviewQuestion`：规范化核心问题、类别、标签和难度。
- `QuestionVariant`：同一核心问题的不同问法。
- `ApplicationQuestion`：题目与岗位之间的关联，保存优先级、准备状态和备注。
- `AnswerOutline`：岗位特定回答提纲及版本。
- `AnswerEvidence`：回答提纲到已确认事实或 STAR 故事的关联。

题目去重优先依据规范化类别和语义相似度。低置信度时由用户选择合并或保留为新题。

### 7.4 事件与统计

- `ApplicationStageEvent`：每次阶段变化的时间戳和来源。
- `ApplicationNote`：联系人、面试、反馈或自由笔记。
- `GeneratedArtifactUsage`：申请最终采用的简历版本和回答版本。

统计从这些原始记录计算，不由 AI 猜测。不同简历版本的转化只描述相关性，不宣称因果。

## 8. AI 处理与事实安全

### 8.1 输入信任边界

JD、简历和用户上传文本都视为不可信数据。内容中的“忽略之前规则”等指令只作为普通文本处理，不能改变系统提示、工具权限或数据访问边界。

### 8.2 简历生成管线

1. 结构化解析 JD。
2. 检索相关的已确认职业事实。
3. 生成要求与证据的映射。
4. 为每个简历内容项生成候选修改与事实引用。
5. 独立验证数字、日期、公司、职位和技能是否有来源。
6. 丢弃无法验证的确定性陈述；将信息不足转换为补充问题。
7. 将通过验证的建议作为草稿呈现。
8. 只有用户接受或编辑后才创建新的简历版本。

### 8.3 面试准备管线

1. 根据岗位要求检索共享题库。
2. 补充可能的岗位特定题。
3. 规范化问题并进行语义去重。
4. 给每道题分配岗位优先级。
5. 检索相关事实与 STAR 故事。
6. 生成要点式回答提纲及证据引用。
7. 用户修改后保存为岗位版本。

系统只能提示“基于该 JD 可能出现的问题”，不能声称知道雇主实际会问什么。

## 9. 异常与恢复

- 简历无法解析：保留原文件，允许粘贴文字或手动建档。
- JD 信息不完整：展示解析结果并要求用户确认公司与职位。
- 没有事实证据：展示能力缺口并提出问题，不生成虚假描述。
- AI 请求失败：保存任务状态和当前草稿，允许幂等重试。
- 导出失败：保留编辑内容，允许重新导出。
- 题目疑似重复：高置信度自动归入已有题，低置信度交给用户选择。
- 用户删除职业事实：未来生成不再使用；历史投递版本保留当时内容快照，直到用户删除对应申请或账户。
- 账户删除：删除原始文件、职业档案、生成文档、投递记录和题库个人数据。

## 10. 技术架构原则

```text
响应式 Web 前端
  -> 应用后端与身份验证
      -> 关系数据库
      -> 私有对象存储
      -> AI 任务服务
      -> DOCX/PDF 文档服务
```

- 桌面端优先支持建档、简历编辑和统计；手机端优先支持查看、更新状态和准备面试。
- API 密钥仅存在于服务端。
- 职业数据、岗位、版本、题库和事件使用关系数据库保存。
- 原始简历和导出文件使用私有对象存储。
- AI 供应商和模型通过服务端适配层调用，业务模块不直接依赖特定模型标识。
- 所有 AI 输出使用固定结构并在服务端验证。
- 解析、生成和导出任务拥有任务 ID、状态和幂等键，可以安全重试。
- 具体框架、云服务和模型在实施计划中依据开发环境、成本和当前官方能力确定，不改变本设计的数据与信任边界。

## 11. 隐私与安全

- 所有用户数据默认私有，并按用户身份实施行级访问控制。
- 文件下载使用有时效的授权链接。
- 应用日志不记录简历正文、JD 正文或可识别个人身份的信息。
- 未确认事实不能用于确定性陈述。
- 用户可以导出全部个人数据。
- 删除账户会删除所有个人文件和派生数据。
- MVP 不使用用户资料训练公共模型。
- 服务端对上传类型、文件大小、文本长度和生成频率实施限制。
- 统计和错误报告只使用去标识化技术信息。

## 12. 测试与验收

### 12.1 自动化测试

- 单元测试：状态转换、证据规则、统计计算、题目合并和版本规则。
- 数据契约测试：AI 输出结构、引用完整性和无效字段拒绝。
- 集成测试：上传简历到建档、JD 到导出、导出到投递记录、投递到题单。
- 安全测试：跨用户访问、恶意 JD 指令、超大文件和非法文件类型。
- 文档测试：将 DOCX/PDF 渲染后检查乱码、截断、错页和文本可读取性。
- 恢复测试：网络失败、重复提交和任务重试不产生重复记录。

### 12.2 必须满足的验收条件

- 每条被展示为事实的生成内容至少关联一个已确认事实。
- 未经确认的数字、日期、公司、职位或技能不能进入最终建议。
- 中文和英文 PDF/DOCX 解析失败时均有可用的手动回退路径。
- 恶意 JD 无法改变系统规则或访问其他用户数据。
- 同一核心面试题可以被多个岗位复用而不复制题目正文。
- 最终投递记录能定位到准确的 JD 快照和简历版本。
- DOCX/PDF 导出内容与编辑器确认内容一致。
- 账户删除后个人数据不再可访问。

### 12.3 Beta 产品指标

以下是验证假设的目标，不是产品承诺：

- 70% 的 Beta 用户完成基础职业档案。
- 60% 至少导出一份定制简历。
- 40% 在两周内创建第二条岗位申请。
- 用户能够说明系统节省了修改简历的时间。
- 事实追溯审计中不出现无法关联已确认来源的确定性陈述。

## 13. 交付行动计划

### 阶段 1：需求验证

- 访谈 5 至 10 位目标用户。
- 收集脱敏后的原始简历、目标 JD 和现有投递流程。
- 验证用户是否愿意维护职业档案、使用定制结果并记录第二次投递。

### 阶段 2：产品与数据基础

- 建立身份验证、职业档案、文件上传和事实确认。
- 完成基础隐私、删除和导出能力。

### 阶段 3：JD 与定制简历闭环

- 完成 JD 解析、要求匹配、补充问题、事实校验和版本化编辑。
- 先保证 DOCX 导出，再完成 PDF 导出验证。

### 阶段 4：投递追踪闭环

- 完成导出后的一键记录、详情页、阶段看板、表格和基础统计。

### 阶段 5：面试准备闭环

- 完成共享题库、岗位题单、去重、回答提纲和准备状态。

### 阶段 6：私有 Beta

- 邀请 10 至 20 位目标用户连续使用两至四周。
- 依据第 12.3 节指标判断是否继续加入付费、求职信、浏览器扩展、外部同步或语音面试。

### 实施边界

这些阶段不是一次性开发任务。每个阶段完成验收后才进入下一阶段，并分别形成聚焦的实施计划。首个实施计划只覆盖“阶段 2：产品与数据基础”；JD 定制、投递追踪和面试准备在各自开始前依据本总设计拆分为独立实施计划，避免把多个子系统压进一次开发周期。

## 14. 设计约束总结

1. 职业档案是唯一可信事实来源。
2. AI 负责提取、匹配、建议和提问，不负责替用户创造经历。
3. 每份简历、每次投递和每套面试准备都有可追溯版本。
4. 通用题只保存一次，岗位通过关联复用。
5. 第一版以手动确认换取可靠性，不用外部自动化扩大风险。
6. 每个阶段必须形成可独立测试的用户闭环后，才进入下一阶段。
